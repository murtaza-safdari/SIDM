# Run 3 signal validation

`era_fingerprint.py` checks, from the content of the LLPNanoAOD files alone, that the private Run 3 production is at 13.6 TeV and that each era carries its own conditions. It reads the 200 GeV / 1.2 GeV / 4.8 mm point of both channels (120 chunks, 100k events per sample and era). sqrt(s) is computed as m(chi chibar)/sqrt(x1 x2), cross-checked against twice the beam energy from the LHE incoming partons, and compared with the generator `comEnergy`. It also measures the pileup profile, the generated and reconstructed vertex positions, and the HLT branch content. The global tag, CMSSW release and HLT menu of every processing step are read from the file's `ParameterSets` and `MetaData` trees, matching PSet IDs by MD5. Two maps show the era-specific dead regions: the 2022EE ECAL endcap region (e/gamma reconstruction efficiency per dark photon to e+e-, 2Mu2E: at least one electron or photon, all objects, within Delta R < 0.1 of either electron, both electrons pT > 5 GeV and 1.5 < |eta| < 3.0 with their production vertex at rho < 110 cm and |z| < 290 cm (before the ECAL face), filled at the dark photon's eta, phi) and the 2023BPix pixel sector (mean number of tracker layers with hits of matched muons). The muon map uses exclusive greedy matching: closest pair first, each reco object used once. The per-object exclusive e/gamma map is kept in the npz, JSON and CSV (`ee_obj_excl_*`), with photons linked to an electron left out of its pool. Its plateau sits near 0.6 because the collimated pairs mostly resolve into a single object. Every quoted region number (threshold, flagged-bin and rectangle averages, bin counts, BPix PF-muon efficiency and its extent at 0.5/0.75/1.0 layers, both matchings) is in `era_fingerprint_regions.json`, and the exclusive values are also in the CSV rows. Usage: `python era_fingerprint.py` (default `--eras 2022,2022EE,2023,2023BPix,2018`; `2018` is the v10 4Mu reference at 13 TeV, and a run over a subset of eras updates only those rows) writes `era_fingerprint.csv` (one row per era), `era_fingerprint.npz` (the histograms; add `--replot` to redraw without EOS) and vector PDFs in `figures/`. The m/sqrt(x1 x2) estimator has a ~2.5% low tail, which is not a beam-energy effect: about 98% of events are c-cbar initiated (2022 4Mu, four chunks), and in the tail events the low-x (x < 1.1e-3) charm parton's mass is not negligible. The LHE estimate has no such tail (99.8% of events within 13598.6-13600.6 GeV). `notebook_figures.py` makes the AN versions of the notebook's three gen-level draft figures (`run3_ctau_representative`, `run3_ctau_grid`, `run3_vs_2018_gen`; inputs cached in `notebook_figures.npz`, `--replot` to redraw). The 180-point cτ scan behind `run3_ctau_grid` is a standalone LHE+GEN job with 500 events per point, run with 2022 conditions (SampleFactory `sidm_run3_production/gen_validate_job.sh`); it does not read the produced samples.

**2018 generator-level requirement (corrected 2026-11).** The 2018 v10 GEN process carries the filter as `genfilter` (GenParticleSelector on genParticlesForFilter) with the cut `(abs(pdgId)==11 || abs(pdgId)==13) && abs(eta)<2.4 && (vertex.rho<740. && abs(vertex.Z)<960.) && pt>4. && isLastCopy() && isPromptFinalState() && fromHardProcessFinalState()`, followed by `gencount` (CandViewCountFilter, minNumber 4). `gen_requirement.py` emulates it on the nano GenPart table: status 1 with the isPrompt, fromHardProcess and isLastCopy statusFlags (the post-FSR final-state copies), pT > 4 GeV, |eta| < 2.4, rho < 740 cm, |z| < 960 cm, at least four per event. `era_fingerprint.py`, `notebook_figures.py` and `run3_lj_eff.py` (`gen_acc_mask`) all use it. On the committed 2018 populations it passes 0.9994 (`era_fingerprint.csv`: 131,014 events in 47 files) and 29057/29073 (`notebook_figures.npz`, 10 files). Every failing event of the 47-file population has a filter lepton whose stored pT is exactly 4.000 GeV and would pass with pT >= 4: nano rounds pT to reduced precision, so a true pT just above 4 lands on the strict cut. The vertex is the stored (smeared) one, whereas the filter read genParticlesForFilter, which is immaterial at 740/960 cm. Earlier versions emulated the filter with a 1 GeV, then a 5 GeV, lepton-pT threshold on the first-copy dark-photon leptons (2018 self-pass 92.3%).

**Gen comparison with 2018.** At 4Mu 200 GeV / 1.2 GeV / 4.8 mm (24 2022 chunks, 10 v10 files; `gen_comparison_summary.json`), 6977/12000 = 0.5814 of the 2022 events and 29057/29073 = 0.9994 of the 2018 events pass the filter. With the filter applied to both, the dark-photon pT mean is 87.98 +- 0.19 vs 87.82 +- 0.09 GeV (+0.18%), lepton pT +0.18%, lepton |eta| 0.954 vs 0.954, pair Delta R 0.0368 vs 0.0369, and mean proper ctau 4.875 +- 0.041 vs 4.802 +- 0.020 mm. Without the filter, Run 3 has dark-photon and lepton pT -8.0% and -8.0% relative to 2018. That is the filter's acceptance, not a generator difference.

**LJ-efficiency scans.** `lj_eff_geom_<era>.json` (geometry mode: loose kinematic preselection, no object ID) and `lj_eff_real_<era>.json` (real mode: the SIDM LJ-source object selection) are produced on condor (`condor_lj_eff/`) from all 120 Run 3 chunks per point and 25 v10 files, with the 2018 filter as the "in acceptance" denominator. Each record carries the requested (`r3_chunks`, 0 = all; `v10_files`) and the read (`r3_chunks_read`, `v10_files_read`) chunk/file counts and the producing commit. In the committed files, the read counts were established after the run (see each record's `provenance_note`): all 25 v10 files open and their entries sum to the recorded n. The Run 3 n equals each sample's total: 120 chunks and 100,000 events, except 2022EE 2Mu2E_800GeV_5p0GeV_5p0mm with 121 chunks and 100,050. `tarball_commit` is null for these jobs; later jobs record the commit stamped into the tarball (`make_tarball.sh`), which `merge.py` checks against the submit-time commit. **Real-mode caveat:** its e/gamma leg uses approximate IDs (electrons without ID, photons `cutBased` >= 1), and each era's own photon ID (2018 Fall17V2, Run 3 RunIIIWinter22V1), so it is not an era-to-era detector comparison (diagnosis below). `lj_eff_summary.py` writes `lj_eff_summary.json`: per mode, era and channel, the mean of the 18 per-point Run 3 - 2018 differences with its statistical error, the RMS, [min, max], the number negative and the chi2 about the mean. The chi2 of the inclusive efficiencies is 21-41 for geometry, 72-333 for real 4Mu and 15,400-15,800 for real 2Mu2E (17 dof; for the exclusive ones 46-198 and 12,300-12,600), so a mean +- stat is not the uncertainty of a common shift. *Real-mode 2Mu2E diagnosis (`lj_eff_real_diag.py` -> `lj_eff_real_diag.json`).* The cause is the photon ID, which is not the same algorithm in the two samples. `Photon_cutBased` is "cut-based ID bitmap, Fall17V2" in the 2018 v10 files and "cut-based ID bitmap, RunIIIWinter22V1" in Run 3 (`Electron_cutBased`: "Fall17 V2" vs "RunIII Winter22"). At the worst point (2Mu2E_100GeV_5p0GeV_40p0mm, 10 Run 3 chunks and 10 v10 files, events passing the 2018 filter), the loose photon ID passes about twice as many photons in Run 3 (71-72 selected photons per 100 events vs 37; electrons 41-43 vs 46). The gen-matched e/gamma LJ is photon-only in 57-58% of events against 30% in 2018. The muon leg passes 88.5-89.3% vs 87.1%; the e/gamma leg passes 76.5-78.2% vs 49.9%. Difference (Run 3 - 2018, 2022 / 2023BPix) at the worst and a mid point (2Mu2E_200GeV_1p2GeV_4p8mm):
- as committed: +24.2 / +26.3% and +7.7 / +7.7%
- photon ID dropped: +0.7 / +1.3% and +0.5 / +1.6%
- photon cutBased >= 2: +10.2 / +9.9% and +2.5 / +1.9%
- photon cutBased >= 3: +5.3 / +5.4% and +2.4 / +2.1%
- electrons cutBased >= 1: +29.0 / +31.3% and +9.4 / +9.8%
- photons removed: -1.3 / -0.7% and +1.2 / -0.6%

Without the photon ID, or without photons, the difference falls to the real-4Mu level (era means +0.72 to +2.14%, per-point range -0.06 to +3.42%). The real-mode numbers are therefore an analysis-like emulation in which each era uses its own e/gamma IDs, not a detector comparison; the ID-free geometry mode is the era-to-era comparison.

`ctau_all_samples.py` measures the proper cτ on every produced sample (180 points x 4 eras, from the LLPNanoAOD GenPart vertices) and writes `ctau_all_samples.csv` and `figures/run3_ctau_all.pdf`.

**Stored precision.** In nano, GenPart_mass is stored with 8 mantissa bits (0.5 GeV steps at 200 GeV, so 34 GeV steps in m/sqrt(x1 x2)) and Generator_x with 14, in both the Run 3 and the 2018 files. The sqrt(s) median is therefore quoted to the storage step, and no width column is given (it would measure storage and line shape). Provenance columns are recorded per process: VtxSmeared, comEnergy and the HLT menu are read from the process that carries them. The generator process's VtxSmeared is compared with the stored GenVtx mean and width (`vtx_pull_*`). In 2018 the only VtxSmeared is in the GEN process (the Realistic25ns13TeVEarly2018Collision values X0/Y0/Z0/SigmaZ = 0.0107682/0.041722/0.035748/3.5 cm, readDB false), while the stored vertex has mean 0.0108/0.0417/0.151 cm and z width 3.20 cm, so its check reads MISMATCH (`vtx_match` False); the Run 3 eras agree. A mismatch never stops the run: it sets `vtx_match` False and prints a WARNING line. No VtxSmeared scenario of the 2018 GEN (CMSSW_10_6_27) or SIM (CMSSW_10_6_17_patch1) release matches the stored vertex (closest: SigmaZ 3.4 cm with the same Z0). The GEN PSet's VtxSmeared parameters are not those of the stored vertex; the smearing step's configuration is not in the file. Every row carries the git commit it was made with (`code_commit`). Its dirty flag checks only the study directory's code (`*.py`, `*.sh`, `*.sub`). The code also depends on `sidm/studies/truth_kinematics_forAN/an_style.py` and `sidm/configs/ntuples/*_v10.yaml` (and the Run 3 location YAMLs), which lie outside that check.


**Productions v1 and v2.** The text above describes the first production (v1: LLPNanoAOD, four eras, `outputs/<era>/`). The scripts take the production as an option: `--production v1|v2` for `era_fingerprint.py`, `notebook_figures.py`, `ctau_all_samples.py` and `lj_eff_summary.py`, `RUN3_PRODUCTION=v1|v2` for `run3_lj_eff.py` and `run3_kin_hi.py` (on the command line the scripts with an option default to v2 and the environment variable to v1; imported, as the notebook does, `notebook_figures` is on v1), and a `PRODUCTION` submit argument for `condor_lj_eff/` (`job_args_v2.txt`, `merge.py WORK STUDY 9 v2`). v2 (EXONanoAOD, five eras with 2024, `outputs_v2/<era>/`) reads the census-checked `signal_run3_v2_<era>.yaml` and writes its own files (`*_v2.*`, `lj_eff_<mode>_v2_<era>.json`, `kin_hi_v2_<era>.npz`, figures in `figures_v2/`); the v1 files are untouched. Differences of v2: 2024 gets both detector maps, and `era_fingerprint_regions_v2.json` adds 2024 read over the regions' bins, 2024's own region search and the v1 regions read in the v2 maps (`*_in_v1_bins`); the 2024 beam spot comes from the conditions DB (VtxSmeared `readDB` true), so its vertex check is marked not applicable; `run3_ctau_all` is drawn from `v2_census/results/ctau_v2.csv` as per-sample pulls (the v2 samples have 100k or 2000 events); `run3_ctau_grid` is not redrawn (it does not read the produced samples); the real LJ mode replaces `DSAMuon_nSegments`, which v2 stores as twice `nDTSegments`, by `nDTSegments + ceil(trkNumCSCHits / 6)`. `v1_vs_v2.py` (no EOS access) puts the numbers of four v1 result files (`era_fingerprint.csv`, `era_fingerprint_regions.json`, `gen_comparison_summary.json`, `lj_eff_summary.json`) beside their v2 values with statistical uncertainties and writes `v1_vs_v2.md`, whose first paragraph gives how many quantities were compared and which differ by more than 2 standard deviations, and whose header lists what is not compared.

**Independence and uncertainties.** The two productions are statistically independent: every job of either production draws its own random seed, and no event is shared. Every v2 - v1 uncertainty relies on that. The uncertainties of the region numbers in `era_fingerprint_regions[_v2].json` (mean tracker layers, PF-muon efficiency) count every muon as independent. The two muons of a dark photon are 0.04 apart in Delta R on average at the 200 GeV / 1.2 GeV point and mostly fall in the same bin of 0.1 x 10 degrees, so fully correlated pairs would make these uncertainties sqrt(2) larger. The e/gamma map is filled once per dark photon and has no such factor.

**The two 2024 tracker regions.** `bp_fixed_2024_A` and `bp_fixed_2024_B` in `era_fingerprint_regions_v2.json` are two fixed rectangles in which the 2024 sample has fewer tracker layers than both 2023 eras (`TRACKER_2024` in `era_fingerprint.py`). Both were chosen on the 2024 maps themselves (A from the search against 2023BPix, B from the 2024 - 2023 map), so a difference read over them is not an unbiased test. Their cause is in the conditions, looked up with `conddb` (not scripted in this directory). Simulation, `140X_mcRun3_2024_realistic_v26` against `130X_mcRun3_2023_realistic_postBPix_v6`: `SiPixelQuality_phase1_2024_v6_mc` disables 14 forward-pixel modules of disk 1 on the minus side (A), and `SiStripBadComponents_realisticMC_for2024_v4_mc` adds seven TID+ modules of disk 3, one of disk 2 and one TEC+ module (B). Data, the tags of `140X_dataRun3_Prompt_v4`, `140X_dataRun3_v20` and `150X_dataRun3_v2` sampled over runs 378981-386951: the same 14 pixel modules are disabled from run 383002 on (inside Run2024F) and not before; the seven TID+ modules of disk 3 are out of the readout cabling from run 375587 on (the end of 2023) and unpowered through 2024. `map2024_ecal_ee_vs_2022` and `map2024_bpix_vs_2023BPix` in `figures_v2/` show the 2024 maps beside the era each should resemble.

**Other outputs in this directory.** `RUN3_EFF_OUT` is the output directory of `run3_lj_eff.py` and `run3_kin_hi.py` when run by hand (default: the current directory); `run3_lj_eff.py` run by hand names its file as `condor_lj_eff/merge.py` does (`lj_eff_<mode>[_v2]_<era>.json`). `kin_hi[_v2]_<era>.npz` hold the generator-level arrays of three points per channel (12 files each) that `run3_kin_hi.py` writes; they were copied here from its output directory, and `run3_study_plots.py` reads them. `trig_grid_<era>.json` (v1 only) are read by `run3_study_plots.py`; the script that made them (`trigger_eff_grid.py`) is not in the repository. In `lj_eff_real_v2_<era>.json` the 2018 block of every record was copied by hand from the v1 files: the v2 jobs had applied the segment-count substitute to the 2018 files too, which changed one event (`v10_provenance_note` in each record); `run3_lj_eff.py` now decides per file.

**Command lines for v2** (from this directory, with the notebook venv; as the usage lines of the scripts give them):

```bash
python era_fingerprint.py --production v2        # CSV, npz, regions JSON, figures_v2/; --replot redraws without EOS
python notebook_figures.py --production v2       # gen-level figures, gen_comparison_summary_v2.json
python ctau_all_samples.py --production v2
RUN3_PRODUCTION=v2 RUN3_ERA=<era> RUN3_EFF_OUT=<dir> python run3_kin_hi.py
# LJ-efficiency scans on condor: the next two lines from a work directory W, with S this directory
$S/condor_lj_eff/make_tarball.sh $W
condor_submit CODEDIR=$S/condor_lj_eff ARGS=$S/condor_lj_eff/job_args_v2.txt R3N=0 V10N=25 COMMIT=<hash> PRODUCTION=v2 $S/condor_lj_eff/submit.sub
python condor_lj_eff/merge.py $W . 9 v2
python lj_eff_summary.py --production v2
python v1_vs_v2.py
```
